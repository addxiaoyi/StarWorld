# 架构与运行边界

## 数据归属

StarCore 唯一拥有国家、城市、成员、领土、科技、政策、繁荣、资源、天气、时代。`CoreBridge` 仅从公开 API 产生不可变 `CoreCity`，反射只调用经审计的公开类型/方法，不读字段、不打包核心、不访问表。无法证明国家/城市存在时停用相关行为。

StarWorld 保存国家文明选择、城市扩展仓储、地区储量、锚点和级别、事件/余波、周期账本、物品凭据与管理员审计。`nation_state` 只是核心 UUID 的扩展信息，不创建国家。孤立扩展状态保留供备份，不因暂时服务缺失删除财产。

## 线程与性能

Paper 主线程读取 StarCore、检查已登记锚点、操作 GUI/背包。不可变快照进入专用 `StarWorld-storage` 单线程处理 JDBC 与纯模拟，提交后回主线程发通知。外部查询 API 返回 Future，不得在服务器线程 join。

定时器每 40 tick 读取一页已登记城市，默认每页 20 城、每城最多 12 设施。ID 分页轮转，任务未结束不叠加下一轮；不扫描所有区块或实体。登记时仅采样锚点一处生物群系；生产只检查已加载区块，绝不强制加载。未加载设施停产。

周期为 epoch 秒整除 period-seconds。重启、长停机、页面延迟后只结算当前周期，不追赶全部遗漏周期。`last_period >= period` 拒绝重放及回拨。正式存档变更周期长度前需停服备份和安排迁移。

## 结算事务

同步核心身份 → 检查账本 → 事件转移 → 每地区每周期恢复一次储量 → 维护 → 顺序配方 → 扣料/储量/入库 → 收据和 last_period，一次 SQLite 事务。任何异常（包括 Error）回滚；共享地区 `last_regen` 阻止重复恢复。矿藏默认不再生，注销不删地区。

输出容量不足则跳过该配方，保留其原料/开采储量；已经支付的建筑维护不退还。闲置但有效的设施仍可能支付维护。最终倍率最多 10，物品数量与每轮任务都有边界。

实体背包与 JDBC 不能原子提交。取出先 PREPARED 扣仓储，存入在 PREPARED 后验证并移除物品；检查整个背包容量，交付后调用 Player.saveData，再完成凭据。失败/崩溃隔离，不自动重放。管理员只能处理不活跃凭据，credit/discard 仅一次并审计。PREPARED 阻止同玩家再开单；活跃 transfer ID 阻止人工处理与交付竞争。

产业账本不重复产出；进程崩溃时玩家存档与仓储仍需人工核对。保存玩家数据不等于分布式 exactly-once，公开事件也不应被监听器重新发放物品。

## Folia

本版不声明支持，检测后停用。StarCore 可变 City/residents/claims、科技/政策和内部 BukkitScheduler 没有跨区线程契约。仅数据库安全不够。

`SchedulerGate` 已分全局、玩家、位置区域操作，预留 GlobalRegionScheduler、EntityScheduler、RegionScheduler。正式兼容条件：核心提供带版本号的不可变国家/城市快照与权限；全局只协调；锚点验证分发各区域；背包/GUI 使用玩家调度器并处理 retired；回执汇总核查归属版本；通过传送、退出、卸载、转国、重启真服测试后才增加 folia-supported。

## 迁移与备份

配置 v1 备份迁移 v2；DB v1 基础表 → v2 审计和索引，DDL 事务提交。拒绝未知高版本，构造失败关闭连接，绝不自动删库。停服备份整个插件目录，避免漏 WAL 和核对凭据。
